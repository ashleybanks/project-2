## Purpose

Defines the field expression system: an optional Liquid expression attached to a `fieldIntent` or `derivedFieldIntent` node, resolved by an LLM from a natural language description and evaluated server-side at render time.

## Requirements

### Requirement: Field intents support an optional natural language expression
A `fieldIntent` node in the block model SHALL support an optional `expression` property containing a Liquid expression generated by the LLM from a user-provided natural language description. The Liquid expression is never shown to the user; only the natural language description is displayed.

The `FrontendFieldIntent` struct SHALL gain `expression: Option<String>`. The PT block model JSON SHALL persist both the user's natural language description (`expression_label`) and the resolved Liquid expression (`expression`).

#### Scenario: Field intent without expression compiles to merge field
- **WHEN** a `fieldIntent` has `field_path` set but no `expression`
- **THEN** the compiler emits `#data.<field_path>` in the Typst source (existing behaviour, unchanged)

#### Scenario: Field intent with expression compiles using expression
- **WHEN** a `fieldIntent` has both `field_path` and `expression` set
- **THEN** the compiler emits the Liquid expression to be evaluated server-side, not the raw `#data.<field_path>`
- **THEN** the server evaluates the expression against the payload before Typst compilation
- **THEN** the evaluated value is injected as a literal into the Typst source

---

### Requirement: Expression editor in the intent chip popover
The intent chip popover in the template editor and in the Preview SVG overlay SHALL provide a natural language expression input. The system SHALL send the input to the LLM and resolve it to a Liquid expression.

#### Scenario: User enters a format description
- **WHEN** a user clicks an intent chip and types "show as month and year" in the expression field
- **THEN** the system calls the LLM (Qwen3-8B, no_think mode) with the field's schema type and the natural language description
- **THEN** the LLM returns a Liquid expression (e.g. `due_date | date: "%B %Y"`)
- **THEN** the expression is stored on the intent and the intent chip shows the `ƒ` indicator

#### Scenario: LLM resolution failure shows error
- **WHEN** the LLM cannot resolve the natural language description to a valid Liquid expression
- **THEN** an inline error is shown: "Couldn't generate an expression — try rephrasing"
- **THEN** no expression is stored; the existing `field_path` behaviour is preserved

#### Scenario: Expression can be cleared
- **WHEN** a user clears the expression input and saves
- **THEN** the `expression` and `expression_label` are removed from the intent
- **THEN** the intent reverts to emitting `#data.<field_path>`

---

### Requirement: Derived field intent for multi-field computations
The system SHALL support a `derivedFieldIntent` inline node as a distinct intent variant from `fieldIntent`. A derived field has no single `field_path`; it has only a natural language description and a resolved Liquid expression that may reference multiple schema fields or aggregate arrays.

#### Scenario: Derived field compiles to server-side expression
- **WHEN** a `derivedFieldIntent` node with an `expression` is compiled
- **THEN** the expression is evaluated server-side at render time
- **THEN** the resulting scalar value is injected into the Typst source as a literal

#### Scenario: Derived field without resolved expression renders placeholder
- **WHEN** a `derivedFieldIntent` has no resolved `expression`
- **THEN** the compiler renders the `expression_label` as plain text (with a `[?]` prefix to make it visible as unresolved)

#### Scenario: LLM receives schema context for derived field resolution
- **WHEN** the LLM resolves a derived field expression
- **THEN** the prompt includes the full template schema, all available field paths and their types
- **THEN** the LLM generates a Liquid expression that references valid schema field paths
